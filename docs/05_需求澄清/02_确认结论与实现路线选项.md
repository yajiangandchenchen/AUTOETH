## 3. 实现路线候选（请选一条）

三条路线**交付物完全相同**（同一套公开接口、同一批样例），差别只在"先做什么、风险在前还是在后"。

### 路线 A：自底向上（协议核心先行）— 推荐

顺序：公开头与类型 → JSON 配置加载 → CRC → schema 编解码 → 线协议 → TP → E2E 14 profile → SD → Runtime → 三个程序 → Classic C 适配 → 安装/消费者。

- 优点：每一层都能独立做纯函数测试，最难的编解码/E2E 最早暴露合同理解偏差；不依赖网络环境即可推进 80% 工作。
- 缺点：`autoethd` 能跑起来的时间最晚（约在后 1/3）；早期看不到端到端演示。

### 路线 B：垂直切片（先跑通一条 RPC，再横向铺开）

顺序：最小可用头/配置/编解码（只支持 VehicleSnapshot）→ UDP+TCP 单方法 RPC → `autoethd`/`autoeth-client` 第一个命令跑通 → 再补全 schema 全类型、TP、E2E、SD、Classic。

- 优点：最快拿到可演示的端到端结果，风险早暴露在集成而不是编译期。
- 缺点：早期实现要为"最小可用"留口子，后补时容易在 TP/E2E/SD 阶段返工编解码与 Runtime；覆盖率要重测。

### 路线 C：合同条款驱动（按文档增量 v1.0→v1.4 顺序）

顺序：按 01→22 号文档、v1.0→v1.1→v1.2→v1.2.1→v1.3→v1.3.1→v1.4 的增量依次落实现。

- 优点：与合同版本严格对齐，评审时最容易逐条追溯。
- 缺点：增量多为交叉修改（同一函数被 v1.2.1/v1.3/v1.4 多次修补），按时间顺序实现会反复修改同一处代码，效率最低。

**推荐 A**：合同是"已冻结的最新版本"，不是演进中的草稿，最终只需实现 v1.4 有效条款；纯函数层最早可测，最符合"证据分离、不要把编译当成功"的要求。
