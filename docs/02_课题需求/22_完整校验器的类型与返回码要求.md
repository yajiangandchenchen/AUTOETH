# Shared full-validator Type/ReturnCode contract

Apply this LOCAL API classification after the current complete public base. Raw header parsing/display and the eight-byte tail canonical extractor retain their own roles. They are not complete-message validation.

| Complete base message type | ReturnCode requirement |
|---|---|
| REQUEST 0x00 | Zero. |
| REQUEST_NO_RETURN 0x01 | Zero. |
| NOTIFICATION 0x02 | Zero. |
| RESPONSE 0x80 | Existing permitted success/application/protocol/E2E domain. |
| ERROR 0x81 | Existing permitted error domain; zero is forbidden. |

For a supported type with a forbidden ReturnCode combination, use existing Native `Errc::MessageType` value 10. Check protocol, service, interface, method, supported type and configured receiving role first. Then check this pair before correlation, payload or E2E. Reject without successful ValidationDecision/business output commitment, application call or Check/SM call. Do not add an enum.

Only when existing reply qualification holds, the received type is REQUEST, the configured target is an ordinary request/response method, and a real error reply is permitted, emit ERROR 0x81 / ReturnCode 0x0A. Copy the original Message ID and Request ID, and received protocol/interface. An earlier protocol-version failure still wins and uses supported protocol version one.

Without current trusted protected metadata, drop a protected-path error; never fall back to an unprotected reply. Fire-and-forget, notification, response and error inputs do not gain error-loop replies. ERROR 0x81 with ReturnCode zero specifically produces local MessageType10, no business dispatch and no response.

The actual receiving role matters. An ordinary requester configured to receive RESPONSE/ERROR may receive a supported but wrong-direction REQUEST: subject to the existing qualification, it can return 0x0A and must not complete its old waiting RPC. An unsupported type such as 0x04 is not a REQUEST and cannot be used to invent a 0x0A response. Provider-side response/FF/notification controls retain no-response behavior. Configured event/FF prohibitions remain even when the incoming type is mistyped REQUEST.

Legal RESPONSE/zero and configured nonzero results remain unchanged. This rule does not introduce a global policy for unknown future ReturnCodes. Existing TP completion/transport roles remain; raw TP types are not unselected by a tail-extractor restriction.

This fixes an observable LOCAL error classification before dependent implementation. It is not an official Native-error-code rule from the standard and is not product execution or defect repair.
