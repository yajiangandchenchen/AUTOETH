# Shared customer contract increment v1.2.1

This version replaces the two text contracts in v1.2 with readable English and incorporates the approved STATIC field-initial destination rule. It preserves all original v1, v1.1 and v1.2 bytes. Both development conditions must receive the same effective input. This document supplies requirements and public configuration, not implementation, private test vectors, review findings or product results.

## Contract precedence and scope

The existing service IDs, element IDs, schemas, E2E bindings, source C declarations and host differences remain in force. No source C enum value or function signature is added. The four discovery/control contracts below come from the selected sources and explicit customer decisions. They do not add a new standard family, full ECU topology, DNS stack or security implementation.

Apply this document after effective v1.1 and the v1.2 files. It supersedes the wording of `08_服务发现与控制策略.md`; the field-initial rule is the substantive clarification. The alignment document in this version supersedes only the wording of its v1.2 counterpart.

## 1. STATIC service relationships

| Public field | Type and default | Meaning and validation |
|---|---|---|
| `provided_services[].discovery_mode` | `DYNAMIC` or `STATIC`; default `DYNAMIC` | Selects the service relationship's discovery mechanism. |
| `requested_services[].discovery_mode` | `DYNAMIC` or `STATIC`; default `DYNAMIC` | Does not disable dynamic relationships elsewhere in the Runtime. |
| `requested_services[].static_endpoints` | Nonempty array for a STATIC requester | Each entry contains `address_family`, `transport`, `local_endpoint`, `peer_address` and `peer_port`. |
| `event_groups[].static_subscribers` | Array on a STATIC provider group | Each entry contains a locally unique `subscriber_id`, `address_family`, `transport`, `local_endpoint`, `peer_address` and `peer_port`. |
| `event_groups[].static_receive_endpoints` | Nonempty array on a STATIC consumer group | References its configured local receive endpoints, including any regular multicast receiver and the required field-initial unicast receiver. |

A STATIC binding inherits the parent's complete, exact `service_id`, `instance_id`, `major` and `minor`. An actual STATIC binding cannot use an `ANY` selector. Each local endpoint must exist and match the declared interface, address family and transport. Peer ports are in `1..65535`. Requester peer addresses are proper-family unicast addresses. Conflicting bindings for the same interface/transport are invalid.

STATIC provider UDP subscribers may use an explicit client-multicast regular destination. TCP destinations must be unicast and use an actual qualified connection. Existing resource, provider, E2E and endpoint rules still apply. The group retains the existing distinct-endpoint multicast-threshold and fanout semantics; this is not a second SD engine.

STATIC-specific fields are not valid on a DYNAMIC relationship. STATIC relationships reject `server_timing`, `client_timing` and group wire `ttl_seconds`: the loader must not insert defaults that create fictional SD timing activity. Each `subscriber_id` is unique within its static eventgroup. It is a local registration identity, not a fabricated four-bit wire Subscribe counter.

### Field-initial destinations

| Static subscriber/group | Initial destination | Configuration rule |
|---|---|---|
| UDP regular destination is multicast and the group contains a field notifier | Explicit `initial_unicast` destination | Required; see the object below. |
| UDP regular destination is unicast and the group contains a field notifier | Existing `peer_address:peer_port` | `initial_unicast` is forbidden as an unnecessary override. |
| TCP subscriber and the group contains a field notifier | Existing unicast destination and actual qualified TCP connection | `initial_unicast` is forbidden. |
| Pure-event-only group | No initial event | `initial_unicast` is forbidden. |

The required object is:

`initial_unicast: { peer_address, peer_port }`

Its family is inherited from the subscriber. The address must be a valid, non-multicast, non-unspecified unicast address in that family. The port must be in `1..65535`. It uses the subscriber's existing same-family UDP `local_endpoint`. The producer must not guess an address from a multicast group, OS hostname, SD port or source port.

A missing required object, an illegal address/family/port or a forbidden extra object returns `InvalidConfig` before start or registration publication. No successful STATIC state or initial-value side effect is published first. The implementation must neither substitute multicast for the initial value nor disable the selected client-multicast capability.

A STATIC consumer group containing a field notifier must name a same-family unicast receive endpoint. For UDP this has a nonzero configured receive port; for TCP it uses the real qualified connection. A regular multicast receiver may be named as well. Matching the two nodes' addresses and ports is a deployment responsibility: a single-node validator cannot establish that the remote process is listening or has received a value.

### Lifecycle and observable effects

A STATIC relationship is enabled or invalidated by its real request, availability, link/IP, transport/provider readiness, resource and Runtime lifecycle. It emits no Find, Offer, Subscribe, ACK, NACK or Stop SD messages for that relationship. Dynamic relationships in the same Runtime continue their own SD traffic.

Native observations use `origin=StaticConfiguration`. Original C current-state enums retain their existing DOWN/AVAILABLE values; there is no invented wire ACK or new C enum value. Static relationships have no virtual wire TTL or retry state.

The provider queues a required field initial on the relationship's first qualified local activation. Pure events have no initial value. Actual I/O failure is reported separately; UDP acceptance does not prove peer receipt. A late consumer may perform the actual getter, which is not evidence that an earlier initial value arrived. Releasing a local request must not pretend that a remote peer was notified.

## 2. ACTIVE and TTL_ONLY client timing

| Input situation | Selected mode |
|---|---|
| Entire `client_timing` object is absent | Existing complete Native ACTIVE defaults. |
| Explicit `mode=ACTIVE` | ACTIVE, even if TTL is its only other key. |
| Explicit `mode=TTL_ONLY` | TTL_ONLY after validating its allowed keys. |
| No mode, and the only explicit key is a valid `subscription_ttl_seconds` | TTL_ONLY, detected before inserting defaults. |
| Explicit timing values of zero | Real ACTIVE values when ACTIVE is selected; zero is not absence. |

`client_timing.mode` accepts only `ACTIVE` and `TTL_ONLY`. TTL_ONLY allows `mode`, `subscription_ttl_seconds`, `subscription_retry_max` and `subscription_retry_delay_ns`. It forbids initial-find, repetition, main-phase and request-response timing keys, including explicit zero values. STATIC forbids `client_timing` entirely.

With explicit TTL_ONLY, a missing TTL defaults to three seconds. A literal only-TTL input must provide a legal TTL. Its domain is `1..0xFFFFFF`; the existing special-lifetime meaning remains intact.

The default `subscription_retry_max=0` creates no retry. An explicit positive uint32 maximum or the string `infinite` uses an explicit positive retry delay or the existing ten-millisecond default. A supplied delay must be positive even with maximum zero, where it is unused. Adding retry keys without a mode is no longer the literal only-TTL form; use explicit TTL_ONLY if that is intended.

Requested and ready TTL_ONLY waits for an eligible Offer, or uses a still-valid eligible cached Offer. It never sends Find. After a qualified Offer it subscribes only to the currently requested groups. There is no request-response delay, so its logical delay is zero; actual backend, kernel and peer observations remain separate.

Offer expiry, Stop and reboot invalidate the old relation and return TTL_ONLY to waiting for an Offer. They do not start active Find. Release, ACK/NACK and stale-epoch retry rules remain unchanged. ACTIVE retains its existing complete search timeline.

## 3. HALF_CYCLE Find replies

| Public field/condition | Contract |
|---|---|
| `server_timing.find_response_mode` | `BASIC_UNICAST` or `HALF_CYCLE`; default `BASIC_UNICAST`. |
| HALF_CYCLE configuration | Requires explicit positive `cyclic_offer_ns`; zero or absent C is rejected for this option. |
| Applicable source guard | MAIN phase, eligible Find and received Unicast Flag one. |
| No actual Offer send fact in the current epoch | Use the basic unicast behavior. |
| `elapsed < ceil(C/2)` | Unicast Offer. |
| `elapsed >= ceil(C/2)` | Multicast Offer. |

`lastOfferTime` is the latest actual complete SD-datagram POSIX acceptance time containing this service's Offer in the current epoch. A datagram containing multiple service Offers updates each service actually included. Queued work, an ActionBatch, backend ownership and EAGAIN do not update this fact.

An actually sent Find-answer Offer also updates this independent fact. It does not reset the selected periodic/repetition due time or counter. Other phases keep their existing behavior.

For integer nanoseconds, compute the threshold as `C/2 + C%2`. Do not multiply elapsed by two or round an odd half down. A current time earlier than the stored time is a clock/precondition error, not unsigned wraparound.

Received Unicast Flag zero is ignored under the existing source rule. Multicast ingress retains its request-response-delay guard; unicast-to-unicast retains the defined exemption. This selector does not change either rule.

## 4. Magic Cookie control messages and reserved names

Raw codec/operations support the exact original 16-byte layouts:

| Field | Client to server | Server to client |
|---|---|---|
| Message ID | `0xFFFF0000` | `0xFFFF8000` |
| Length | `8` | `8` |
| Request ID | `0xDEADBEEF` | `0xDEADBEEF` |
| Protocol / interface version | `1 / 1` | `1 / 1` |
| Message type | `0x01` | `0x02` |
| Return code | `0` | `0` |

Runtime direction comes from the established TCP connection's actual client/server role, not solely from its incoming message type. Only a complete frame at the current boundary with the correct direction and every fixed field is consumed as a valid control Cookie. It is never application data and receives no response.

A wrong direction or corrupted field is not a valid Cookie. Apply the existing framing/type/error-eligibility diagnostics without creating an error loop. A bad length remains a real framing/connection error. Periodic Cookie insertion and arbitrary payload scanning/resynchronization are explicitly not selected MAY mechanisms. No unused enable flag or additional recovery mode is introduced.

The reserved key names `hostname`, `instancename`, `servicename` and `otherserv` retain their claim lookup/display meaning. They are not authenticated identity. There is no automatic hostname query, required presence, trimming or duplicate overwrite rule. Non-SOME/IP business advertising remains unselected; raw `0xFFFE`/`otherserv` decode and display remain supported.
